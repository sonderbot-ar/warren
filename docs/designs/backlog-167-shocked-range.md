# Backlog #167: the shocked range on pipeline runs, and the range in the pipeline report

Issue: https://github.com/sonderbot-ar/warren/issues/167 · Branch `backlog-167-shocked-range` · Version v0.9.16 when merged.

## Problem

Brief question 5 and design principle 4: the student sees the range of the forecast actually shown. Since v0.9.8 any run has the baseline's range (`run_ranges.run_ranges`, `basis: "baseline"`, note `baseline_only`), but a pipeline run shows a shocked forecast (the Monte Carlo paths, report section 2), and its range is not built. M9 builds the shocked ("combined") range only for backtest cases (`ranges.shocked_samples`, M9 design "With shocks"). And the pipeline report, the one document a run leaves behind, has no range at all: #144 deferred it because `reproduce` compares the report again, and a range moves if the stored misses change.

## What changes

1. **The shocked range on any simulation.** `run_ranges(conn, run_id, n=None, check_basis=True, sim_id=None, coverage=True)`. With `sim_id`, the simulation must belong to `run_id` (else `EvaluationError`, as for an unknown run). The samples are the simulation's own: `montecarlo.sample_lines(load_assumptions(run_id), load_simulation_shocks(sim_id), n_samples, seed)` with the simulation's stored seed and sample count, which are the draws its stored bands came from (`reproduce_simulation` checks that). Each shocked sample gets one drawn past miss, M9's method unchanged (`ranges.ranges` on those samples, the misses filed by the run's date, both pools). `basis` becomes `"shocked"`, `sim_id` names the simulation, `n_samples` is the simulation's, and the range seed is `ranges.range_seed(f"{sim_id}:shocked", pool)` (M9's `<subject>:<variant>` key, the simulation as subject). Without `sim_id` nothing changes: `basis` `"baseline"`, the same seeds and numbers as v0.9.8 (a test), `sim_id` None.
2. **The centre the band is read against.** Each quarter keeps `revenue_forecast` and `ebit_forecast` (the baseline's, as before) and gains `revenue_center` and `ebit_center`: the median of the samples the misses are applied to. For the baseline they equal the forecast; for a shocked range they are the shocked p50, the number the report's section 2 shows. `revenue_vs_forecast` and `ebit_vs_forecast` are measured from the centre, so for a baseline range they are unchanged.
3. **What the shocked range assumes.** A run-level note replaces `baseline_only` on a shocked range: `shocked_plus_misses` (params `sim_id`), "the range adds the baseline's past misses to each shocked sample; when a shock captures an event the baseline would have missed, part of that miss is counted twice, so the range leans wide" (the assumption M9 states, M9 design "With shocks"). And `coverage_is_baseline`: the track record beside it is the baseline range's (M9's rolling test has no shocks); M9's shocked coverage exists for the 26 backtest cases only.
4. **`coverage=False`** skips the track record (the slow part, about 12 seconds; `coverage` is then an empty list and a note `coverage_skipped` says so). The report uses it for the shocked variants, since their track record is the baseline's, already computed once.
5. **The range in the pipeline report.** `PipelineState` gains `range_errors_sha256: str | None` (the `pairs_sha256` of the misses known on the as-of date), set by the `write_report` node beside `actuals_on`. When it is set, the report gets a section "Range from past misses" after the hindsight section (section 6 or 7; the trace moves down one): per basis (the baseline, then each variant with a simulation) a table of quarters 1–4 with the pooled band's p10, p50 (the centre for the forecast column), p90 for revenue and EBIT in millions; the pooled track record for all companies and this company, one line per item (share inside, interval, verdict); and the notes' English text. Pipelines finished before this have no `range_errors_sha256`, so their reports render exactly as before (a test), as #128 did with `actuals_on`.
6. **Reproduce names the cause.** `python main.py reproduce --pipeline-id P` adds a line: `OK range misses <first 12 hex>` when the misses known on the as-of date still hash to the stored value, `MISMATCH range misses: stored …, now …` otherwise, counted as a failure, the rule M9's `reproduce_build` applies ("the errors the build read have changed"). The report comparison stays as it is, so a changed miss also shows there; the extra line says why.

**Point in time.** Unchanged from v0.9.8: misses filed by the run's date, coverage from origins dated before it with actuals filed by it. The simulation's shocks were sized from news known by the as-of date (M6, `known_by`), and the simulation is stored.

**Nothing new is stored** apart from the hash in the pipeline state (a JSON checkpoint field, no migration). LLMs produce no number: the range is `financial_math` on stored samples and stored misses.

## Steps

- **Step 0.** This design doc.
- **Step 1.** `run_ranges` with `sim_id` and `coverage`, the centre fields, the notes. Tests (`tests/evaluation/test_run_ranges.py`): without `sim_id` the dict equals v0.9.8's apart from the new fields (`sim_id` None, centres equal to forecasts); with a stored simulation, the bands equal `ranges.ranges` on `sample_lines` with the simulation's seed and n and the `"{sim_id}:shocked"` seed; with zero-width shocks (low = base = high = 0) the shocked bands equal the baseline bands drawn with the same seed (M9's own check); the centre is the samples' median; `vs_forecast` is measured from the centre; a simulation of another run raises; `coverage=False` gives no cells and `coverage_skipped`; the notes on each basis; the same call twice gives the same dict. CLI: `ranges run --run-id R --sim-id S [--json]`, tests in `tests/evaluation/test_cli.py`. Exit: green.
- **Step 2.** The report section and the state field. Tests (`tests/orchestration/`): a state without `range_errors_sha256` renders byte for byte as before; with it, the section appears with one table per basis (baseline, then each simulated variant, a variant without shocks not repeated), the trace's section number moves by one; `write_report` stores the hash; `reproduce` prints `OK range misses` and, after a stored miss is changed, `MISMATCH range misses` and exits 1. Exit: green.

Results written below. Exit: numbers recorded.

## Alternatives considered

- **Store the range rows per pipeline (a new table) and render the report from them.** The report would always reproduce, even after misses are rescored. Rejected for now: the misses change only when the scoring code changes (they are point-in-time by construction), and then M9's own builds already fail reproduce on purpose; one rule for both is simpler. If #162 rescoring lands, its PR re-renders the affected reports.
- **Put the range inside section 2 (Paths).** Closer to the numbers it qualifies, but it renumbers nothing only if it is a sub-section, and section 2 is per variant with every period through year 5, while the range stops at quarter 4. A section of its own after hindsight keeps old reports byte-identical and reads as "how sure, from the record".
- **Re-run the track record per shocked variant.** Rejected: it is the baseline's rolling test either way; computing it three times triples the time for the same numbers.
- **Take the range seed from the pipeline's case id (`<TICKER>_<date>:llm_masked`), as M9's case build does.** Rejected: a pipeline can have several simulations per run (different seeds or sample counts), and the simulation id is the one key that names exactly one set of samples.

## Product impact

Serves brief Q5 and principle 4 for the forecast actually shown on a pipeline run. New for the app: `run_ranges(conn, run_id, sim_id=S)` and `ranges run --sim-id S`; `to_dict` gains `sim_id`, and each quarter `revenue_center` and `ebit_center`. `basis` can now be `"shocked"`. New codes: `shocked_plus_misses`, `coverage_is_baseline`, `coverage_skipped`. Changed meaning: `revenue_vs_forecast` and `ebit_vs_forecast` are measured from the centre, which for a baseline range is the forecast as before (no change for existing calls). Nothing renamed or removed. Which simulation goes with a screen: the pipeline state's `sim[variant].sim_id`; masked is the headline variant (M8).

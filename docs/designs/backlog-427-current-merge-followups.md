# Backlog #427: the current portion merge (#421), three follow-ups

Issue: https://github.com/sonderbot-ar/warren/issues/427 (from the #425 gatekeeper and analyst reviews of `docs/designs/backlog-421-current-lease-debt.md`) · Branch `backlog-427-current-merge-followups` · Version v0.9.82.

## Background

Since v0.9.81 (#421), the current portion of long-term debt is filed under two map items: `debt_current` (`LongTermDebtCurrent`, debt only) and `debt_current_with_leases` (`LongTermDebtAndCapitalLeaseObligationsCurrent`, debt plus the current finance-lease portion). When a reader asks for `debt_current` and the map in force has the second item, `facts.get_facts` reads both plus `debt_noncurrent` and merges them per balance date into one `debt_current` (`_merge_current`, `domains/fundamentals/facts.py` lines 1085–1105), choosing with `current_on_noncurrent_basis` (lines 1063–1082): the lease-inclusive figure when the same date's non-current debt is lease-inclusive, it is above the plain figure, and it is not the non-current debt again (a mis-tag). Only Exxon and Coca-Cola file the lease-inclusive tag.

## Problem

1. **Pairing on fiscal labels.** `_merge_current` keys each fact by `(period_start, period_end, fiscal_year, fiscal_period)`. Each item's fact for a date carries the fiscal labels of the filing row it was read from. If the plain and the lease-inclusive figure for one balance date ever carried different labels, they would not be paired: both would come back as `debt_current` at the same date, and every reader would see two current portions there. Separately, a single map item gets one fact per fiscal label in annual and quarterly mode (`_one_per_period`, line 891, the later date wins); the merged item is built from two items, each deduplicated on its own, so if the plain figure sat at one date and the lease-inclusive one at another date with the same label, both would come back under that label. Before #421 the two tags were one item and neither could happen.
2. **Order.** When the merge runs, `_merge_current` sorts by the order the items were asked for, then by date (lines 1104–1105). Without the merge, `_get_facts` returns facts sorted by item name, then by start and end date (reported: `_facts`, line 142, sorting the `_rows_by_period` keys) or by item name and end date (annual: `_get_facts`, line 1166; quarterly: `_quarterly`, line 1041). So asking for `["debt_noncurrent", "debt_current"]` returns the two items in a different order depending on whether the map has the new item.
3. **A rounded plain figure.** The lease-inclusive figure includes the plain one, so it can only be smaller when one of the two is rounded. If the plain figure is rounded up (Exxon's 2025 10-K tags "$6.2 billion" as 6,200M under `LongTermDebtCurrent`) and the lease-inclusive one is precise but lower (say 6,180M), the rule keeps the rounded plain figure because the lease-inclusive one is not above it. The same rule picked correctly at Exxon 2025-12-31 only because 6,234M happens to be above 6,200M.

**On today's data none of the three changes a figure.** A survey of all eight companies (AAPL, MSFT, WMT, KO, PG, JNJ, CAT, XOM) at seven as-of dates (2012-06-01, 2015-06-01, 2018-06-01, 2020-04-01, 2022-06-01, 2024-06-01, 2026-11-15), both modes (latest, first reported) and all three frequencies (reported, annual, quarterly), on a copy of the restored snapshot with its concepts synced to today's map: no balance date where the three items carry different fiscal labels; no date where an item has two facts; no date where the lease-inclusive figure is below the plain one (the analyst confirmed the last on the same filing and date: equal at Exxon 2020–2024, 6,200M against 6,234M at 2025-12-31). Asking `["debt_current"]` and `["debt_noncurrent", "debt_current", "cash"]` on each of those 336 combinations (672 queries), 358 queries come back in a different order from the unmerged read of the same names (the merge runs for every company, since the item is in the map). The survey scripts are run-only, not committed (the results are their output, as for #421's Step 4). This is a robustness item: it makes the merge behave like a single map item by construction.

## Plan

- **Step 0.** This design doc.

- **Step 1. The merged list in the unmerged order.**
  - `facts.py`: one function, `_in_query_order(facts, frequency)`, gives the order `_get_facts` returns: reported by (item, start, end), with an instant's missing start first, as `_facts` sorts its keys; annual and quarterly by (item, end). `_get_facts` uses it in place of its annual sort, and `_merge_current` sorts its result with it (`get_facts` passes the frequency down). Python's sort is stable, so ties keep the order of the wide list, which `_get_facts` already sorted the same way.
  - The reading rules' fingerprint changes. The order of a list cannot change which figure a run reads: the readers key facts by item and fiscal label or date (`reported.py` lines 268–288, `harness.py` 160–162, `propose.py` 129–131; the analyst checked them), and the one case where the order could pick the winner, two facts under one key, is what Step 2 removes. So `reading_rules.md` gets a new row with version 9 (no bump) saying so, as its rules allow for a change that cannot change a read. The Step 3 builds are the backstop.
  - Tests (`tests/analysis/test_current_merge_order.py`, fixture `make_company` from `tests/analysis/conftest.py`, with Exxon's presentation `lease_inclusive()` from `tests/analysis/test_current_lease_debt.py`): for every mode and frequency, with the items asked in an unsorted order (`["debt_noncurrent", "debt_current", "cash"]`), `get_facts` returns the same (item, start, end) sequence as `_get_facts` for the same names.
  - Exit: full suite and ruff clean.

- **Step 2. Pairing on the date alone, one fact per fiscal label, and a rounding margin.**
  - `_merge_current` keys each fact by `(period_start, period_end)` only. Each item has at most one fact per date in every mode and frequency (`_rows_by_period` keys by item, start and end, line 85; `_facts` makes one fact per key; `_one_per_period` only removes facts), so a date pairs at most one fact of each of the three items. The merged fact keeps the chosen figure's tag, value and filing, as today; its fiscal labels are the plain figure's when both are filed (the single item before #421 took the newest row of its first-ranked tag, the plain one, so a date stays where it was placed then), else the chosen figure's own.
  - In annual and quarterly mode the merged `debt_current` facts then go through `_one_per_period`, the rule every single item already obeys: one fact per fiscal label, the later date wins. Reported mode keeps one fact per date, as for any item.
  - `current_on_noncurrent_basis`: with the other conditions unchanged (non-current lease-inclusive, plain figure not negative, lease-inclusive figure not equal to the non-current debt), the lease-inclusive figure is also taken when the plain figure is above zero and looks rounded to ten million or more (`SMALLEST_ROUNDING_UNIT`, 10^7: filers state their statements in millions, so only a coarser rounding, "$6.25 billion" or "$6.2 billion", is a rounding of text), the lease-inclusive one is zero or above, below the plain one by no more than half the plain figure's apparent rounding unit, and itself has a smaller apparent unit (more precise). This is XBRL's own reading of a rounded figure: a value with `decimals` −8 stands for the range within half of 10^8 of it (XBRL 2.1, section 4.6; *Precision, Decimals and Units 1.0*, 2017), so 6,180M lies inside a "6.2bn" and the two figures do not contradict each other. Company facts carry no `decimals` (`financial_facts` stores `value` as REAL in dollars and has no decimals column; the −8 at Exxon 2025 was read from the inline XBRL by hand in #421), so the unit is inferred from the figure: `rounding_unit(value)` is the largest power of ten, up to 10^12, that divides `int(round(abs(value)))`, and 0 for a zero figure (no margin). 6,200,000,000 → 10^8; 1,617,000,000 → 10^6. So 6,180M beside a plain 6,200M (half-unit 50M; 6,180M's unit 10^7) is taken; 6,140M (60M below) is not; a lease-inclusive figure below a plain figure precise to the million (half-unit 0.5M) never is, since filers in millions report nothing finer; and a plain zero (AAPL and MSFT file 12 of them) opens no margin, so a negative lease-inclusive figure is never taken over it (analyst).
  - `READING_RULES_VERSION` 9 → 10 with its row in `reading_rules.md`: both rules can change what a run reads on some data, though no fact does today.
  - Tests (in `tests/analysis/test_current_lease_debt.py`): the two items at one date with different fiscal labels give one `debt_current` there, carrying the plain figure's labels (the guard: built by editing the lease-inclusive rows' fiscal labels in the fixture database), in every mode and frequency; two dates under one fiscal label give one fact in annual mode (the later); `rounding_unit` on 6.2e9 (10^8), 1.617e9 (10^6), 1.617e9 as a float sum (still 10^6), 0 (0) and −5e6 (10^6); 6,180M beside 6,200M is taken; 6,140M is not; 1,616M beside a plain 1,617M is not; a plain zero beside a negative lease-inclusive figure keeps the zero; a precise 1,700M beside 1,660M is taken (the known limit, pinned); a rounded plain figure still loses to the mis-tag guard (a lease-inclusive figure equal to the non-current debt); a rounded plain figure with no lease-inclusive tag at its date is read unchanged (AAPL files 14 plain figures that look rounded to 10^8); the existing #421 tests unchanged.
  - Exit: full suite and ruff clean.

- **Step 3. Real data.** On a copy of the restored snapshot (concepts synced to today's map): every stored run's date (the 903 runs that are not what-ifs) built fresh in memory through today's map, each pinned to the market downloads it stored (`runs.price_fetch_sha256`, `index_fetch_sha256`, `yield_fetch_sha256`, as `runs.rebuild` pins them) and its stored choices, once on `main` and once on this branch: expected identical rows and note codes on every date. The survey above repeated: the merged facts identical as sets to `main`'s for every company (CAT's maturities tag included), mode, frequency and as-of date, and every query now in the unmerged order. `reproduce --all --rebuild`: every stored run reproduces to the cent and rebuilds as before (each through its own map).

## Alternatives considered

- **Pair on the date, but refuse (raise) when the fiscal labels differ.** A refusal stops a run over a labelling difference that changes no figure; the labels come from one fiscal calendar per company (`ingest.place_period_end`), so a difference would be a calendar renumbering between two filings, which `_one_per_period` already settles for single items.
- **Return the merged list in the asked order and document it** (the issue's first option for item 2). Readers don't depend on the order today, but a merged and an unmerged read of the same names should not differ in anything but the chosen figure; matching costs one shared function.
- **A fixed rounding margin** (say 1% of the plain figure). It would also take a lease-inclusive figure that is below a precise plain figure, where the filing contradicts itself rather than rounds; the apparent unit only opens the margin when the plain figure looks rounded.
- **Read `decimals` from the filing.** The SEC's company facts API, Warren's source, does not carry it; reading each inline XBRL document is a new ingest for a case no filing shows today.
- **A symmetric margin** (professor and analyst): also take a rounded lease-inclusive figure below a precise plain one (6,200M beside 6,234M), when the two ranges overlap. Not taken: neither figure is then right, and the precise plain figure's error (the leases inside the gap, at most 34M there) is no larger than the rounded figure's (up to half its unit, 50M); the rule keeps the precise figure. Every lease-inclusive figure filed today is precise to 10^7 or finer (analyst).

**Limits.** A plain figure that is precise but happens to end in zeros (1,700M exactly) looks rounded to 10^8, so a lease-inclusive figure up to 50M below it and more precise would be taken (pinned by a test). A filer whose lease-inclusive current portion is below its debt-only one contradicts itself whichever is right; the lease-inclusive figure is the one consistent with the lease-inclusive non-current debt D3 counts. A rounded lease-inclusive figure below a precise plain one keeps the plain one (above).

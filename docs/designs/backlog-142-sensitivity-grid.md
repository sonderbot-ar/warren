# Backlog #142: sensitivity grid, value per share over WACC and terminal growth

Issue: https://github.com/sonderbot-ar/warren/issues/142 · Branch `backlog-142-sensitivity-grid` · Version v0.9.12 when merged.

## Problem

The front-end team's request R2b (brief question 9, `docs/product/brief.md` §3: "¿Qué tan sensible es el valor de Coca-Cola al WACC y al crecimiento terminal?"). The classroom DCF exercise is a table of value per share over WACC and terminal growth. Today a run stores one value per share and the two ERP ± 1 standard error values (`dcf.outputs_and_gaps`); the what-if (v0.9.9) changes inputs one request at a time and cannot set WACC at all, because WACC is an output of CAPM and the capital weights, not a row (#171).

The brief asks for: the grid with the run's own point marked; the lesson that under Warren's terminal method (value driver, RONIC = WACC, Structure Guide Decision 4, oct.30.2026) the table is almost flat along growth and steep along WACC; the textbook Gordon model beside it for contrast; and cells where growth reaches WACC shown as "no value" with the existing reason, never as zero, under both methods (v0.5.4, #79).

## What changes

A new module `domains/analysis/sensitivity.py` with `grid(conn, run_id, wacc_steps=None, growth_steps=GROWTH_STEPS) -> Grid`, and a command `python -m domains.analysis sensitivity --run-id R [--wacc-steps=-0.02,-0.01,0.01,0.02] [--growth-steps=-0.01,-0.005,0.005,0.01] [--json]` (a list that starts with a minus must be written with `=`, or argparse reads it as an option).

1. **The two axes.** Each axis is a list of shifts from the run's own value, in fractions (0.01 = one point): WACC from the run's WACC (`dcf.base_wacc`), terminal growth from its `terminal_growth` row. The run's own 0 is always added (an explicit 0 is fine; a step given twice is `duplicate_step`), the list is sorted, and then it must hold 2 to 9 values (`too_few_steps`, `too_many_steps`, params `axis`, `count`, `min`, `max`); a NaN or infinite step is `invalid_input` (params `axis`). So the run's own point is always in the grid (`run_point`: `row`, `column`; rows are WACC, columns growth). Growth default: −1, −0.5, 0, +0.5, +1 point. **WACC default:** −2, −1, 0, +1, +2 points, leaving out any step whose WACC is less than half a point above the run's terminal growth (`DEFAULT_MIN_GAP`; note `default_step_left_out` with the steps). Terminal growth is the risk-free rate on every run (4.98% on 2026-10-30), and Coca-Cola, Johnson & Johnson and Exxon have WACCs 1.5 to 2 points above it, so the −2 point row would be almost all "no value" (analyst). Steps the caller names are taken as given. The grid also returns each axis's absolute values (`wacc_values`, `growth_values`), so the app never adds.
2. **WACC set directly, as a teaching override, in memory only.** `dcf.Inputs` gains an optional `wacc_override` (default None). When set, it is the WACC (`Valuation.wacc`), every period's discount rate and the roll-forward rate to the as-of date; the cost of equity, the weights and every cash flow stay as stored. With `wacc_override` None, `dcf.compute` is unchanged, so every stored run reproduces as before (tested: `reproduce --all` on the real data, and tests that override = the run's own WACC gives the run's outputs bit for bit, including a property test). An override with a cost-of-equity shift (the Monte Carlo's) is refused (`DCFInputError`). Nothing is stored: a cell is not a run, and WACC is still not an input of any stored run (#171).
3. **Terminal growth moves the terminal value only.** A growth step changes `terminal_growth` and nothing else; the explicit revenue growth path keeps its stored values. This is the textbook table, and differs on purpose from the what-if, which refades the path (v0.9.9 item 3); note `growth_path_held` (params `what_if`: the command for the other reading).
4. **The run's method and the contrast.** Each cell is valued under the run's own terminal method (`method`: `value_driver_ronic_wacc` since M4, `gordon_fcff` before) and under the other one (`contrast`), labelled as a contrast. The run's choice is untouched. The Gordon contrast is Gordon on year 5's stored FCFF, the formula Warren used until the owner replaced it (Decision 4, oct.30.2026), because its reinvestment does not follow growth. The review showed how far that goes on real companies (analyst: implied return on new investment from −159% at Apple to 226% at Procter & Gamble), so the contrast is shown with what it implies rather than repaired: the block's year-5 `reinvestment_rate` (1 − FCFF ÷ NOPAT, `fm.reinvestment_rate`), each Gordon cell's `implied_ronic` (g ÷ that rate, `fm.implied_ronic`; Damodaran, *Investment Valuation*, ch. 12; None when the rate is not positive), the note `gordon_holds_reinvestment`, and `gordon_reinvestment_not_positive` when the company reinvests nothing in year 5. Repairing Gordon with a RONIC (NOPAT × (1 + g) × (1 − g/RONIC)) needs a RONIC: equal to WACC it is Warren's own formula; any other is a new assumption without a source in the rows. The note `ronic_follows_wacc` says the value-driver table is flat along growth by its assumption (RONIC = WACC), not by a finding about the company, and that each WACC row moves that assumed return (professor).
5. **A cell.** `wacc`, `terminal_growth`, `wacc_step`, `growth_step`, `value_per_share`, `change_pct` (against the run's point in the same block, `fm.growth`) with `change_pct_gap` (`no_value` when this cell or the run's point has none, `base_not_positive`; checked here before `fm.growth`, which would raise), `terminal_share` (None when the enterprise value is not positive), the formula's numbers for the app's Fórmula tab (`terminal_base`: Y5 NOPAT under value driver or Y5 FCFF under Gordon, `terminal_value`, `pv_explicit`, `pv_terminal`, `enterprise_value_as_of`, `equity_value`), `implied_ronic` (Gordon only), `thin_spread` (WACC − growth under the run warning's 3 points, `math_engine.TERMINAL_SPREAD_WARNING`) and `gap`. A cell with no value has every number None and `gap` coded with params `wacc` and `terminal_growth`: `rate_not_positive` when WACC ≤ 0 (the grid checks this itself for both methods, because the Gordon formula has no such check, so a cell never has a value under one method and none under the other; explainer, analyst, professor), `growth_not_below_rate` when growth reaches WACC, `rate_not_above_minus_100` as `dcf.NO_VALUE_REASONS` has it. Any other `FinancialMathError` is raised. The run's own point under the run's method equals the stored `value_per_share` exactly; if it ever did not, the grid refuses (`run_does_not_reproduce`).
6. **The lesson as numbers, and a verdict by a stated rule.** Each block has `wacc_spread` and `growth_spread`: along the run's own column (WACC) and row (growth), between the lowest and highest steps that have a value (`low_step`, `high_step`, `low_value`, `high_value`, `low_change_pct`, `high_change_pct`, and `per_point`: the change as a fraction of the run's value per point of the input, `fm.change_per_point`; `gap` `fewer_than_two_values` or `base_not_positive`). Per point, so axes of different widths compare. `growth_to_wacc` = |growth per point| ÷ |WACC per point|. The note `flatter_along_growth` holds when the value-driver block's ratio is below Gordon's, `not_flatter_along_growth` otherwise, `lesson_not_shown` when either ratio is missing (params `value_driver`, `gordon`). The professor's point is the reason for the ratio: Gordon is steeper on both axes; what differs is how growth compares with WACC. The app shows the verdict and never judges a threshold itself (product lead).
7. **Notes.** `sensitivity_not_range` (a sensitivity, not a range of outcomes: design principle 4), `wacc_set_directly` (params `run_wacc`), `growth_path_held`, `contrast_method` (params `terminal_method`), `ronic_follows_wacc`, `gordon_holds_reinvestment` (params `reinvestment_rate`), `gordon_reinvestment_not_positive`, `growth_above_risk_free` (columns to the right of the run's assume growth above the risk-free rate forever, when the run ties growth to it; analyst, Damodaran ch. 12), `default_step_left_out`, and last the lesson verdict.
8. **What the call returns.** `Grid.to_dict()`: `run_id`, `ticker`, `as_of`, `currency`, `wacc_steps`, `growth_steps`, `wacc_values`, `growth_values`, `run_point`, `method` and `contrast` (each a block: `terminal_method`, `terminal_formula` (the what-if's coded formula), `reinvestment_rate`, `cells[row][column]`, `wacc_spread`, `growth_spread`, `growth_to_wacc`), `notes[]`. A what-if child may be the grid's run.

**Point in time.** No data is read: the grid revalues the run's stored rows, which were point in time on the run's date. Nothing it computes is newer than the run.

**LLMs.** None. Every number comes from `dcf` and `financial_math`.

**Storage and reproducibility.** Nothing is stored and no migration is needed. The grid is a pure function of the run's stored rows and the two step lists; a test calls it twice and compares, and counts the stored rows before and after.

## Alternatives considered

- **Each cell as a stored what-if child** (the issue's "on the what-if revaluation"). Rejected: 25 to 81 stored runs per question, none of them a run anyone would reopen, and a direct WACC cannot be a stored row until #171 decides what it means for the cost of equity and weights. The grid reuses the what-if's pieces that fit (its terminal formulas and coded notes) and stays in memory.
- **Move WACC through an input that is a row** (ERP or beta, solved so WACC moves by the step). Rejected: the student asked about WACC; a hidden ERP that lands on the right WACC is a trick, it moves the weights' cost of equity too, and with no equity weight it cannot reach some WACCs.
- **Refade the revenue growth path with terminal growth, as the what-if does.** Rejected for the grid (item 3): it mixes a change in the explicit forecast into the column, so the table no longer shows the terminal value's sensitivity, which is the textbook object and the brief's lesson. The what-if keeps its rule; the note names the difference.
- **Absolute axis values instead of shifts.** Shifts keep the run's point in the grid by construction and let one default work for every company; absolute values are returned for display.
- **Any two inputs.** The issue says "first use"; the other pairs (margin × growth, beta × ERP) can be added with the same cell code when a brief question asks for them.

- **The Gordon contrast is inconsistent on real companies (analyst 1, professor B2).** Year 5's FCFF carries reinvestment that does not follow g: implied return on new investment −159% (Apple), 226% (Procter & Gamble); Gordon at the run's point is 2.5 to 4 times the run's value at JNJ, XOM and PG. Repairing it would need a RONIC with no source in the rows (item 4).
- **Coca-Cola loses its WACC spread (analyst 2).** The default WACC axis now leaves out steps within half a point of growth, and spreads are per point between the ends that have a value, so they work with gaps (items 1 and 6).
- **WACC ≤ 0 under Gordon (explainer B2, analyst 3, professor B3).** The grid checks it itself for both methods (item 5).
- **The lesson is true by assumption (professor B1)** and **the app can't judge it (product lead B1).** Note `ronic_follows_wacc`; a per-point ratio and a coded verdict by a stated rule (item 6); a test that the value-driver ratio is below Gordon's.
- **Doc fixes (explainer B1, B3, B4, G1–G9).** `--wacc-steps=` with `=`; `change_pct` checked before `fm.growth`; the Step 2 test calls `dcf.compute` with the override; the step counting rule, an explicit 0, NaN, no-value fields, spread ends, `rate_not_above_minus_100`, `Valuation.wacc` under an override, when each note appears, and the block fields are now stated.

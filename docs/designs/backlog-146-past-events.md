# Backlog #146: past events, by rule

Issue: https://github.com/sonderbot-ar/warren/issues/146 · Branch `backlog-146-past-events` · Version v0.9.34 when merged.

## Problem

The front-end team's request R5 (brief questions 10–15, `docs/product/brief.md` §3 "Eventos" and §5). Every *evento* answer must show past cases chosen by a stated rule, never by hand and never by an AI: for each case the company, date and source, how close it is to the question, what Warren forecast just before, what was reported after, quarter by quarter, and that miss beside Warren's usual miss for the company on quarters without an event, so an ordinary error is not read as the event's effect. It always shows how many cases there are (n), says when that is too few, warns when an acquisition changed the company's scope, and lists metrics to watch for that kind of event, each with a source. The owner's direction in #130: the impact of an event is never an LLM's output.

Today the cases, their baseline runs and their scores are stored (M3, M8), but there is no query: the app would have to pick cases itself.

## What the data is

- **The case library**, `domains/evaluation/cases.csv` (M3): 26 rows, 18 events of seven types (`guidance` 6, `restructuring` 4, `m_and_a` 3, `litigation` 2, `regulation` 1, `supply_chain` 1, `macro` 1) and 8 rule-dated `control` rows. Each has a source URL, a description, a horizon of 4 quarters, and `scope_change` text where a deal closed inside the horizon (MSFT ×3, KO, XOM, JNJ), each with the consolidation date ("consolidated from 2023-10-13") and a horizon label ("(h1-h4)", "(h3-h4)", "(h4)"). Three of the labels are off by a quarter (MSFT_2023-01-18, MSFT_2023-10-13, XOM_2023-10-11: the labelled first quarter ended before the deal closed; analyst B1), which never mattered before because the backtest drops whole cases (`backtest.py`, `no_scope`). This call reads the date.
- **Each case's baseline run**: the backtest batches store one `baseline` row set per case in `eval_results`, and on the restored data every case has exactly one baseline run id across all three batches (`<case_id>_1`; query in Step 3). The run is made from data public the day before the event (M3's look-ahead guard).
- **What was reported after**: `hindsight.against_actuals(conn, run_id, actuals_on)` (v0.9.7, #128) already gives each forecast quarter of a run beside its first-reported actual in the filings public by a date, scored as M3 scores it, with the filings behind it and coded gaps (`not_reported`, `restated_basis`, `other_ebit_definition`, `zero_base`). It is point-in-time on the actuals.
- **The usual miss**: M9's monthly origins (`forecast_origins`, `baseline_errors`): the same baseline model run on the 1st of every month since 2019-04, scored per target quarter and horizon. v0.9.14's track record deduplicates them to one row per (target quarter, horizon), from the first origin that made the forecast (`track_record._group_rows`), keeping only rows whose actuals were filed by the date asked.

## What changes

A new call `domains.evaluation.past_events.past_events(conn, ticker, event_type, as_of=None, now=None) -> PastEvents`, and a command `python -m domains.evaluation past-events --ticker T --event-type E [--as-of D] [--json]`. It writes nothing. Without a date it uses `shared_kernel.calendar.last_ended_day(now)` and says so (`as_of_default`), as v0.9.7's commands do. `ticker` is the company the question is about; `event_type` is one of the case library's event types other than `control`, or a type that has metrics to watch but no case yet (today only `policy`: elections and changes of government policy, brief Q13), so a question with no analogue gets n = 0 and the metrics instead of a weak same-type match (product-lead B1). Anything else is refused with the code `unknown_event_type` (`event_type`, `allowed`). The question reader does not name an event type today (`webapp/reader/reading.py`); the screen gets it from the reading card or a menu, and the front-end files the reader change as its own issue (product-lead B4).

1. **The rule.** From `cases.csv` (read with `cases.load_cases`, so its validation applies), the call takes every case with `event_type` equal to the one asked, of any company, whose `event_date` is before D (an event after D had not happened yet). These are `cases`, and only these count in n. Controls and any type not in the file (M10's `grid` rows live in their own file, `grid_cases.csv`, and are never read) are never included. The rule's text and the case file's SHA-256 are in the answer (`rule`, `cases_sha256`), so the same file and date always give the same list.
   - Also returned, as context and **not** counted in n: `same_company_other_type`, the asked company's own cases of other types before D (brief Q12: Apple's February 2020 case is "close" to a supply question though it is filed as `guidance`). Each says its type.
   - Order: same company first, then by event date, newest first.
2. **Closeness**, per case: `same_company` (its ticker is the one asked), `same_type` (true for `cases`, false for `same_company_other_type`) and `same_mechanism`, which is **null** with the note `mechanism_untagged`: one type mixes mechanisms (the six `guidance` cases are an inflation cut, a currency cut, a supply cut, an earnings miss and two raises), so a same-type case is not necessarily the same mechanism (product-lead B2). #147's theme tags fill it. `direction` (same or opposite, brief Q14) is null with the note `direction_not_recorded` until #147 records it.
3. **Per case**: `case_id`, `ticker`, `event_date`, `event_type`, `description`, `source_url`, `scope_change` (the file's text or null), `run_id` (the baseline run), `run_as_of`, and per forecast quarter 1–4 (`horizon_quarters` of the case):
   - from `hindsight.against_actuals(conn, run_id, D)`: `period`, `period_end`, `horizon`, and per item (`revenue`, `ebit`) `forecast`, `actual`, `miss`, `signed_miss` (positive: Warren forecast too high), `miss_unit`, `filings`, `missing` (its codes, unchanged);
   - `forecast_margin` and `actual_margin`: EBIT ÷ revenue, through `financial_math.ratio`, null when either side is missing (the brief asks for operating margin; the EBIT miss is already in margin points of actual revenue);
   - `ended_before_event`: true when the quarter ended before the event date (it was forecast because it was not yet reported). 8 of the 18 event cases have such a first quarter (analyst B3; XOM_2023-10-11's 52.6% miss on the quarter ended 2023-09-30 is oil prices, not Pioneer). Its miss is shown and not compared (`usual` null-valued with the code `ended_before_event`), for every type: the call cannot tell which guidance cases came with that quarter's results;
   - `scope_change`: true when the quarter's `period_end` is on or after the consolidation date in the file's text (`from YYYY-MM-DD`); the "(hN)" label decides only for text without a date or a quarter not yet reported. On those quarters the miss is shown but not compared with the usual one (`usual` is null with the code `scope_change`): most of that gap is the acquired company's revenue being added, which the backtest also leaves out (`backtest.py`, M8);
   - `usual` per item: Warren's usual miss for **the case's company** at **the same horizon**, on target quarters without an event, from the monthly origins known by D. The grain is #145's: one row per (target quarter, horizon), from the first origin dated before D that made it, both items' actuals filed by D (`track_record._group_rows`); the miss is recomputed from forecast and actual with `harness.score` (absolute, revenue over the actual, EBIT over the actual revenue), the same scoring `hindsight` uses, not M9's stored log error (explainer B2, B4). Fields: `n_quarters`, `median_miss` and `p90_miss` of the absolute misses (same unit as the event's miss), and `rank`, the share of those usual misses smaller than this quarter's miss (0.95: larger than 95% of the usual misses). `beyond_usual` is true when the miss is above `p90_miss`. With fewer than 12 usual quarters (M9's and #145's minimum) `beyond_usual` is null with the code `few_usual_quarters`. A quarter with no actual yet, or a coded gap, has `usual` null.
   - **Which quarters are "without an event"**: the company's (period, horizon) rows of the monthly origins, less every target period that any of the company's event cases **dated before D** (any type; an event after D was not known yet, explainer B3) forecast at horizons 1–4 in its baseline run, less the periods a control's `scope_change` covers (JNJ's Abiomed quarters; product-lead idea), less the quarters v0.9.7's basis detector flags (`run_ranges.basis_flags`, filings public by D) for either item on any origin of the group, since a change of reporting basis is not a forecast miss. The percentiles use `statistics.quantiles(..., method="inclusive")`. 2020's pandemic quarters stay in unless an event case covered them (CAT's control keeps FY2020Q2–Q3; analyst idea); the note says so.
4. **n and thin evidence.** `n` is the number of `cases` with at least one quarter reported by D; `n_compared` those with at least one quarter compared with the usual miss (professor idea: a case whose quarters are all scope-changed adds no comparison); `n_listed` all `cases`. `thin_evidence` (code `thin_evidence`, params `n`, `threshold`, `reason`) is a reading rule, not a test the call runs. Reason `few_cases` when `n` is below 6: if every case had missed by more than the company's usual **median**, an exact two-sided sign test (M8's `backtest.sign_test`) would need 6 cases to reach p < 0.05 (5 of 5 gives 0.0625; 6 of 6 gives 0.031); the text says six makes a test possible, not that it proves anything (professor B1). Reason `direction_not_recorded` otherwise: until #147 records each case's direction, a type's cases may point opposite ways (P&G and Coca-Cola raised guidance, four others cut it), so no count is enough (analyst B2). So today every answer is thin, which is true. With n = 0 the answer has `missing` `no_cases` (`event_type`, `as_of`): brief Q13's "No hay casos parecidos".
5. **Metrics to watch**, a checked-in table `domains/evaluation/event_metrics.csv` with columns `event_type`, `metric_id`, `metric`, `where_to_find`, `source`, `source_url`: two or three rows per askable event type, each sourced to a US GAAP topic or an SEC Regulation S-K item that requires the disclosure, so a student can find it in the 10-K or 10-Q; guidance itself is voluntary, so its outlook row cites Form 8-K Item 2.02, where it is furnished, and says it is voluntary (analyst idea). Loaded and validated (every askable type has at least one row, every row has a source, no unknown type, `metric_id` unique within a type: `segment_results` and `regulatory_effects` repeat across types on purpose) by `past_events.load_metrics`; the answer returns the asked type's rows and the file's SHA-256. The text is English; the front-end translates it.
6. **Notes** on every answer: `rule` (the selection rule in words), `baseline_only` (the forecasts are the baseline's, without news shocks), `usual_from_monthly_forecasts` (the usual miss comes from the monthly forecasts, at the same horizon, on quarters without an event, known by D, including 2020's quarters), `beyond_usual_by_chance` (about 1 in 10 ordinary quarters is also beyond the line, so one unusual quarter does not show the event caused it: up to 8 cells per case, professor B2), `past_outcomes_not_forecast`, `mechanism_untagged`, `direction_not_recorded`, `thin_evidence`. Each note's `text` is its English wording for the translators.

## Alternatives considered

- **Take the case's forecasts and actuals from `eval_results`.** Rejected: the M8 batch stores no `actual_filed_at`, so a cut at D would need its scoring recomputed anyway, and `against_actuals` already does that point-in-time with the same scoring and coded gaps. Step 4 checks the two agree.
- **Compare with the company's usual miss over all quarters.** Rejected: the event quarters would be inside the "usual" set, and a large event miss would raise the yardstick it is measured against. Event studies estimate the normal outcome outside the event window (MacKinlay 1997, §4).
- **Estimate the usual miss only from quarters before the event** (the classic estimation window). Rejected for now: the monthly history starts in 2019-04, so the 2019 and 2020 cases would have almost none. All non-event quarters known by D are used, and the note says so. A pre-event window can be added when the history is longer.
- **Pool the usual miss across companies.** Rejected: the brief asks for the company's own usual miss, and #145 showed companies differ (CAT, XOM).
- **A threshold for thin evidence from Kahneman & Lovallo (1993).** They give no number. The sign-test minimum is a stated, checkable reason; it is a working rule, not a literature value, and the note says what it means.
- **Let the AI pick or rank analogues.** Rejected by the owner (#130) and by Decision 9.

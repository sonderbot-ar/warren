## Problem

Warren's engine answers the brief's questions from the command line (`docs/product/brief.md`; six work today, five in part). Students need them in a browser, in Spanish, with every number one click from its source (design principles 2 and 3). Decision 13 fixes the shape: a web app that runs on the owner's Mac first, nothing hosted, no cost, and that can be hosted for a school later without a rewrite. It also needs a model for the question reader that Decision 9 records (owner, nov.03.2026: "no menus first"). Neither the stack nor the reader's model has been chosen; both go to the owner on one card.

## What the stack must do

Each line comes from a standing rule or a signed-off document; the comparison below scores every option on them.

1. **Call the engine as a library** (Decision 11, guardrail 4). The engine is Python (`domains/`, `shared_kernel/`); the app imports it and never edits it. So the server is Python.
2. **Free, with a licence that allows a paid product** (Decision 12's rule: no GPL, AGPL or non-commercial), and runs on the owner's 16 GB Apple Silicon MacBook.
3. **Hostable later without a rewrite** (Decision 13): one process and the SQLite database, deployable to any host or a school's own server.
4. **Pristine look under our full control** (owner, nov.03.2026; design principles, "How Warren looks"): our own tokens, type scale and number rules; no framework look we fight against.
5. **The interactions the principles name:** the reading card before anything is computed (6), the side panel with five tabs on every figure (2), the what-if with its ripple (8), wide tables that scroll in their own frame, phone width with the panel full screen.
6. **Accessible in both themes** (principles, "How Warren looks" and "The bar"): light and dark, WCAG AA contrast, full keyboard use (the panel's tabs by arrow keys, focus into and back out of the panel, Escape to close), screen readers told what changed after a partial update, touch targets of at least 24 × 24 px.
7. **Spanish first, English by a toggle, numbers by region** (brief §1; principles, "Numbers": Mexico by default, 1,234.5 or 1.234,5 by region). Text apart from logic (guardrail 5), and the engine's coded notes (#172, `reported.Coded`) translated in one place (the app's text catalogues, keyed by code).
8. **Point in time on every request.** Every page carries its *fecha de corte* in its address (`?corte=2026-11-03`); a request without one is redirected to the last day ended in New York (`shared_kernel.calendar.last_ended_day`, as the engine's commands do since v0.9.7), so every engine call has an explicit `as_of` (standing rule).
9. **Testable in CI**: ruff and pytest as today, plus one added CI step that runs Playwright (Apache-2.0) and its Chromium for keyboard runs and screenshots at 1440 px and 390 px for the `design-critic`.

## Options compared

Versions are today's releases, to be pinned in Step 1. Licences checked on PyPI and npm (nov.04.2026).

Spanish and regions | Babel formats numbers and dates by region on the server (es_MX, es_AR, en_US) and holds the text catalogues; one place for every number's format | Either the API sends numbers already formatted by Babel, or the browser formats them (`Intl`, same CLDR data); both work, at the price of a second toolchain | Mixed; framework widgets format numbers their own way |
| 8. Point in time | Each route takes `as_of`; checked by pytest | The same, in the API | The same |

| Languages to maintain | Python, HTML, CSS, a little JavaScript | Python and TypeScript, two build tools | Python |
| Cost | Free | Free | Free |

**Recommendation: A.** It is the only option that meets every line without a second language or a framework look. Its edge over B is one language and one toolchain to maintain and test, with every number formatted by one Python function by region, next to the engine that produced it. The interactions the principles ask for are each a server round trip that the engine has to make anyway (a what-if is computed and stored by `domains.analysis.whatif.revalue`), so client-side state buys little. If a later screen needs heavy client interaction (a live chart the student drags), a single component can be added on that screen without changing the rest; B stays the fallback. C is ruled out on lines 4 and 6: the owner asked for pristine, and these frameworks' widgets, their behaviour and their keyboard handling are not ours to change.

Charts are chosen at the visual direction, among free options that render on the server or with one small script (inline SVG from Python, or Observable Plot, ISC).

## The question reader's model

Decision 9 records the reader: it returns only labels (the kind, the company, the date, the inputs it names, values copied word for word), code checks every field, and the student confirms the reading. It is measured on a labelled set of student questions before students use it. The model behind it:

| | 1. A local open model (about 8B parameters, 4-bit) | 2. Claude Haiku through Warren's existing key | 3. No model (menus only) |
|---|---|---|---|
| Cost | Free | Paid per question (small, but a cost; and per student once hosted) | Free |
| Runs on the Mac | Yes, through Ollama (MIT) or llama.cpp (MIT) with Metal; about 5 GB of memory | Needs the network | Yes |
| Licence | An Apache-2.0 model such as Qwen3-8B, picked by Decision 12's rules (safetensors or GGUF, no remote code) | Anthropic's terms | n/a |
| Answers as fields | Output held to a JSON schema by the runtime's grammar | Tool use with a schema | n/a |
| Hosted later | Needs a server with about 8 GB of memory, a cost decided at hosting | Cost per call | n/a |
| Owner's earlier answer | Fits "free tools only" | A cost: owner's call | Rejected as the primary path ("no menus first"); kept as the fallback |

**Recommendation: 1**, behind one interface (`read_question(text, locale) -> Reading`, where `Reading` holds the kind, company, date, the inputs named with any value copied from the question, and an unsure flag; a field that fails the code check is dropped and the reading is marked unsure, so the reading card asks the student) so the model can be swapped without touching the screens, as data sources sit behind adapters (guardrail 1). The front-end team picks the exact model in Step 3 by Decision 12's rules and the score on the labelled set. If the local model fails the bar, the team comes back with a card for option 2 and its measured cost.

**Step 3b. The reading card's rules, as code (may start before M10; no screen).** Added nov.09.2026: the owner took Haiku behind the confirm card at its measured error rate (nov.08.2026), so what the card asks before anything is computed now carries the safety the 2% line was meant to give. They do not depend on M10's outputs, only on the reading, so they are built and tested now, apart from any template; Step 4 draws the card around them. Nothing is computed from a reading in this step and no model is called.
  1. **`webapp/reader/card.py`**, `card_for(reading, question, last_ended_day, region) -> Card`: a checked `Reading` in, the card's content out as data. `Card` holds the reading, the parsed value of each input (or none), `asks` (what the student must answer before *Calcular* is offered) and `notes` (what the card must say), each a code with params, so its words live in the catalogues (`card.ask.<code>`, `card.note.<code>`, Spanish and English) and the logic holds none. `ready` is true only when there are no asks and the reading computes something (item 3).
  2. **Parsing a copied value** (`parse_value(value_text, region) -> Value`, or `Unreadable` with its ask): the number and its unit, read by code from the span the reader copied (the check already proved it is in the question, with its digits and separators as typed). Units: percent, basis points ("pb", "bps", "puntos básicos", "basis points"), percentage points ("punto", "point", "pp", "punto porcentual"), a plain number (beta, a share count), money (a "$" or "dólares"; "mil", "millones", "mil millones", "millardos", "billion", "B" scale it; "billón" is asked, 10^9 or 10^12), a multiple ("el doble", "doubled", "la mitad", "halved") and a method word ("Gordon"). A leading minus (also an en or em dash, as word processors type it) or parentheses make it negative; a sign in words ("menos") is left to `direction`. On beta, three digits after a mark are asked, as on a rate. Number words, only when the span has no digits: "cero", "zero", "un", "una", "uno", "a", "one", "full", "medio", "half", "cuarto", "quarter", "dos", "two", "tres", "three"; an article right before a fraction or "full" is one word ("un cuarto", "a full point", "half a point"); any other pair ("un punto y medio") is unreadable, and a number word needs a unit ("a lot" is unreadable). **Separators:** a comma or point followed by one or two digits is a decimal mark in any region. Followed by exactly three, it is read as the region's group mark only on an amount or a count ("US$5.000 millones" in Argentina is 5,000 million); it is **asked** (`value_ambiguous`, both readings shown) when it is the region's decimal mark ("5.000" in Mexico, "1,250" in Argentina) and always on a rate ("4,125%"), where a thousands group makes no sense. Both marks follow the region strictly. A value with two numbers, a dash between numbers, or "entre"/"between" is a **range**: never a level, and never its first number (part 3). A value naming a Latin American currency is asked in dollars (`value_currency`). The parsed amount is the student's own number read by code; nothing is computed from it here.
  3. **Asks**, in this order (`card.ASKS`): `reader_unsure` (the reading is unsure or a field was dropped, out of scope or not: the card shows the menus beside it, Decision 9's fallback); `company_missing` (a *dato*, *estimación*, *cambio* or *evento* with no company, listing the eight; the brief's examples omit the company for brevity, but every answer is about one); `value_range` (the two ends shown as typed, in `text`; the student picks a value or the sensitivity grid); `value_missing` (a *cambio* input with no value, never given or dropped by the check; offers the grid too); `value_missing_via` (a Fed move with no size: it asks the move, in basis points); `value_currency`; `value_ambiguous`; `value_unreadable`; `percent_or_points` (a rate moved by "%" with `how` add: "el margen baja 10%" is ten points or a tenth of its level); `points_or_bp` (ten or more "puntos" on a rate: the Spanish financial press often means basis points); `fed_surprise` (a Fed move whose question does not say "sorpres…", "inesperad…", "imprevist…", "surprise" or "unexpected": an expected move is already in the yield and changes nothing, brief §2 and Kuttner 2001, so the card asks before pushing it through the transmission); `wacc_and_parts` (WACC set and one of its parts changed: with WACC fixed the other change does nothing); `driver_periods` (a change to a driver, `dcf.DRIVERS`, always: next year only or every forecast year; the reading has no period per input, so Step 4 may pre-select from `period`); `method_unknown` (a `terminal_method` value other than Gordon, such as "múltiplo de salida": Warren has no exit-multiple method, f023). `ready` is true only with no asks and a kind that computes: an out-of-scope card never offers *Calcular*; a price question links to an *estimación* instead.
  4. **Notes**, in this order (`card.NOTES`): `corte_default` (no `as_of` in the reading: the *fecha de corte* is the last ended day, named; a period such as "el último trimestre" is not a *fecha de corte*) or `corte_from_question` (the date read, shown to confirm, day first in Spanish); `fed_move_is_event` (an input reached through `via`: the value is the Fed's move, which the transmission's sourced range turns into a change in the 10-year yield, never one for one); `relative_change` (a rate moved by "un 20%" with `how` scale: a share of its level, not points); `cash_unchanged` (`shares` changed with neither `debt` nor `cash_and_investments`, either direction: the cash paid or received is left as it is, so value per share moves for nothing, Miller and Modigliani 1961; it tells the student to change debt for a buyback, since the what-if moves the shares with it, v0.9.27); `wacc_bypasses_parts` (WACC set directly; it names every part, the weights and the tax shield included); `usd_only` (the question names pesos, reais, soles, "en reales" or a currency code, as whole words: Warren reports in US dollars and converts nothing); `intrinsic_value_offer` or `intrinsic_value_offer_target` (a `precio_o_consejo` reading: the brief §4 answer; the second when the question says "precio objetivo" or "target price"). Out-of-scope readings get no *fecha de corte* note; their other answers (another company, a concept, no question) are the screen's, from brief §4.
  5. **Not in this step:** the card's look and its template (Step 4, mockup first); conversation context for follow-ups (Step 4); saying that an event inside a *cambio* is the student's own assumption (part 1, rule 2), because the reading has no field for the event, so code cannot tell "si hay recesión y el margen baja" from "si el margen baja"; it goes to Step 4 as a reader field or a fixed line on every *cambio* card, to be chosen with the mockup; the input's current level beside the student's value (Step 4, from the run); whether students read the card or just confirm it (automation complacency, Parasuraman and Manzey 2010), measured once screens exist.
  Tests (`tests/webapp/test_card.py`): each ask and note on a question that needs it; the parser on every unit, number word, sign and the separator rule in Mexico, Argentina and English; a range in every listed form; every code has text in both catalogues within its params; `ready`; the card over all 405 stored labels in three regions raises nothing, gives no amount to a range, and every value is read or asked; in Mexico only "US$5.000 millones" is asked; and Haiku's seven confident errors on the fresh exam (part 3), each with what the card does. ### Step 3 results, part 1: the set, the check and the bar (nov.05.2026)

Step 3 is done in two parts, so the bar and the labels are fixed in `main` before any model sees the set: part 1 (this) is the labelled set, the code check and the scorer; part 2 writes the reader's prompt, runs the candidate local models (Decision 12's rules) and records the score.

- **The set:** `webapp/reader/labelled_set.jsonl`, 204 questions (105 in Spanish, 99 in English): the brief's 15 in both languages and its out-of-scope examples (35), 35 variants by the product lead, and 134 questions the `student-reviewer` wrote in two batches without seeing any label (typos, no accents, *vos* and *usted*, tickers and nicknames, "25pb", "3T24", "31/12/2023", Walmex and KOF beside Walmart and Coca-Cola, follow-ups with no company, "en pesos"). Every kind has at least 10 questions; each line keeps a short `why` for the hard labels.
- **Held out:** the 134 `student-reviewer` questions (66%) are a part the product lead did not write. The report scores them on their own, and the reader's prompt in part 2 may quote none of the set's questions (a test will check it; Dwork et al. 2015 on reusing a holdout).
- **Frozen:** a test pins the file's SHA-256. A label can change only before a run, with a new hash and a line here saying which and why.
- **The reading** (`webapp/reader/reading.py`): `kind` (`dato`, `estimacion`, `cambio_de_supuesto`, `evento`, or `fuera_de_alcance` with a reason: `precio_o_consejo`, `otra_empresa`, `concepto`, `sin_pregunta`), `companies` (tickers from the engine's `universe.csv`), `as_of`, `period`, `inputs` (each `name`, `how` (`set`, `add`, `scale`), `direction`, `value_text`, `via`) and `unsure`. Inputs are the engine's `DRIVERS` and `SINGLE_VALUES` less the market value of equity and the roll-forward years, plus `wacc` and `terminal_method` (brief §2); the one transmission is `fed_policy_surprise` → `risk_free` (#143).
- **The code check** (`check`): drops any name outside the vocabularies, any company outside the universe, any `as_of` after the last ended day or whose year is not in the period copied from the question, any value or period not copied from the question (up to case, accents, punctuation and filler words: "7,5%" is not "7.5%", and "un punto" is not "punto"), any input on a kind other than a *cambio de supuesto*, and any transmission that does not reach its own input; then the reading is unsure. A direction sent with a level, and any date on an out-of-scope reading, are dropped without doubt (the level says it; nothing is computed). Malformed model output is an unsure reading, never an error. The score is taken after this check, on what a student would see.
- **Labelling rules** (the ones a reader could get wrong):
  1. The brief's order: a *cambio* when every change asked for is a model input; an *evento* when the question names an event and no input change; else *dato* (a filed figure or ratio) or *estimación* (a model output, including the model's track record and a default sensitivity grid). The brief's "an input with a value" is read with its own §2 ("Who sorts", point 1): a value not in the question stays blank for the student to fill in on the card, so a *cambio* may arrive without one (brief Q9 has none).
  2. When a student turns an event into an input change themselves ("si hay recesión y el margen baja un punto"), it is a *cambio*: the change is named and the event is the student's reason. The card must say the event is the student's assumption and that Warren does not measure it. A buyback with no number moves two inputs (shares and the cash paid), and borrowing to build something moves debt and capex: each is an *evento* whose card offers both (more debt alone would cut equity value for nothing, the same Modigliani–Miller point); where the student names only the share count (q083), the card must say the cash paid is left unchanged, since cutting shares alone raises value per share for nothing (Miller and Modigliani 1961).
  3. `how` is `set` for a level ("fuera 1,2", "baja a 15%", "from 18% to 21%"), `add` for a move in the input's unit ("sube 50pb"), `scale` for a proportional move ("un 20%" of capex, "doubled"); `direction` only with `add`, `scale` or no value. `value_text` is the number and its unit, nothing more ("25 puntos básicos", "half point", "Gordon"); a value in another unit (working capital in days) is not copied. **With `via`, `value_text` is the size of the event** (the Fed's move), never the input's: the transmission's sourced range turns it into a change in the 10-year yield (about a third of a basis point per basis point of surprise, Kuttner 2001), and the card shows it as the Fed's move. A Fed move without "sorpresa" is read the same way; the card says an expected move is already in the yield (brief Q7).
  4. `period` is any date or period named, copied; `as_of` only when the question sets a *fecha de corte* for a model output or a change, as a day or as the end of a named year or quarter ("a fines de 2024" is 31 Dec 2024). A balance date on a filed figure is a period, not a *fecha de corte*. "Hoy", "now" and "en el pasado" are neither; nor is "every year" on a driver (Step 4 asks which periods). An out-of-scope reading keeps no date. Day-first dates ("03/04/2025") are 3 April in Spanish; the card shows the date to confirm.
  5. Out of scope: a price or advice question wins over another company; a trading multiple ("¿a cuántas veces EBITDA cotiza?") is a price question. Named companies in the universe are kept even when the question is out of scope. Walmex, KOF and FEMSA are other companies.
  6. Ambiguous questions are *eventos* and the card offers the inputs (brief §2): "¿y si le va mal?", "growth slows" (revenue or terminal growth), a follow-up that names nothing readable alone ("¿y para Microsoft?", "and if it were 3%?"). The reader sees one question at a time; conversation context is Step 4's.
  7. A question that asks a *dato* and a *cambio* together is a *cambio*; its period is kept.
- **The bar** (`webapp/reader/score.py`, `BAR`, tested so it cannot move quietly): a reading is right when its kind (with the out-of-scope reason), companies, `as_of` and inputs (name, how, direction, value, transmission) all match. Kind right on at least 95% overall and 90% in each language; companies on 95%; `as_of` on 95%; inputs exactly right on 90%; a wrong reading without the unsure flag on at most 2%; unsure on at most 15% (more would make the menus the main way in, against "no menus first"). The period span is scored and shown, not in the bar, because its edges vary harmlessly ("2024" against "fiscal 2024"). The labels score 100% against themselves (tested).
- **What the bar can show:** it is a point threshold, not a proof. The report prints each share with its 95% Wilson interval. With 204 questions, 95% observed has an interval of about 91–97%, so a pass says the reader is likely above 90%, not that it is at 95% (Wilson 1927; Brown, Cai and DasGupta 2001); the 2% ceiling on confidently wrong readings shows only that the rate is low (0 of 204 bounds it below about 1.9%).
- **Run it:** `python -m webapp.reader.score --answers ANSWERS.jsonl` (one `{"id", "reading"}` per line; a missing answer counts as unsure and wrong); exit 0 when the bar is cleared.

## Alternatives considered

- **Wait for M10 before choosing a stack.** The Build Plan's first order. The owner chose (nov.04.2026) to compare stacks now, since the stack does not depend on the engine's outputs; screens still wait.
- **A desktop app.** Rejected in Decision 13 (installs and a copy of the data on every school machine).
- **Django instead of FastAPI.** Its login and admin tools help once there are users, which Phase 1 does not have, and logins are a separate owner decision. FastAPI is smaller; moving the templates later costs little, since they stay plain Jinja-style HTML.

## Engine needs

None for Step 0 or Step 1. The app imports the engine's existing calls: `domains.analysis.reported.reported_period` (reported figures with their filings), `domains.analysis.whatif.revalue` (what-ifs), `domains.analysis.runs.run_baseline` (a run on a date), `domains.evaluation.run_ranges` (a run's range and its track record, v0.9.8), `domains.evaluation.hindsight` (what was reported afterwards, v0.9.7) and `shared_kernel.calendar.last_ended_day` (today's *fecha de corte*). It reads and writes the database through `shared_kernel.database.get_db_connection` (existing; SQLite in WAL mode, so engine writes do not block the app's reads).

**Rules for sharing the database** (engine lead's review):
- Each route opens its own connection inside its body (`with get_db_connection() as conn:`), never through a dependency that can cross worker threads (the connection keeps SQLite's same-thread check).
- The app never applies migrations. At start it compares `current_schema_version` with `list_migrations` and refuses to start, with a message naming the command, if they differ.
- The app writes only when a student asks for something new (a what-if, a run on a date with none stored), never on a page view. (The first draft also put every write behind one lock in the app, because run ids were counted outside the write; v0.9.10, #176, moved that count inside the engine's own write lock, so the app needs none.)
- A write that waits past SQLite's 10 s timeout (during a long ingest) shows the designed error state and can be retried.

**Asks filed for the first screen:** a structured source for every forecast assumption (today a run's filings are only inside the free text of each assumption's `method`; principle 2 needs them as fields) (#175), and run ids allocated inside the transaction (#176, before hosting). Already open: #172 (warnings as codes, so they show in Spanish), #145 (the company's track record) and #142 (the sensitivity grid). Also noted: the "filings may be out of date" note lives only in the command line (`domains/analysis/__main__.py`), and `code_version()` reads git, so a hosted copy without `.git` would store runs as "unknown"; both go into the first screen's asks if it needs them.
